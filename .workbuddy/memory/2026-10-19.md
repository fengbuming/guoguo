## 8998 完全版资源实测 + VPS 适配评估（用户拟迁至 2C1G / 30Mbps / 40GB / 月1024GB 流量）

- 后台启动 `dist/juku.exe -open=false`（PID 19728），实测完整播放链路（viewer → playback/open → playback/stream 与 hls native）。
- 关键数据：
  - 空闲 RSS 106–186MB（library.json 50MB / 27,722 部全量在内存）；15 线程。
  - MSE 单流 78.5MB/34.7s（≈18Mbit/s）CPU 仅 +0.23s；2 路并发 129.7MB、CPU +0.44s、RSS +2.7MB。每 10Mbit/s 代理吞吐 ≈0.4% 单核、+1–3MB。
  - Native HLS（手机路径）：整集一个 ffmpeg 进程连续封装（RSS ~142MB），135s 1080p 全程 ~11s CPU（`-c copy` 封装非真转码）；占 "video" 额度（默认 1，故同时仅 1 路）。分片命中缓存后 1ms 级响应。
  - 并发上限来自 `data/playback-settings.json`（默认 会话4/媒体8/remux2/音视频转码各1/预备1/封装缓存512MB）；超限返回 429「同时播放数量已达上限」；会话空闲 10 分钟（playbackIdleTimeout）回收。
  - 1080p 竖屏（1080×1920）单片 147.6s / 78.5MB / 4.25Mbit/s → 1.53GB/观看小时。
- 结论：2 核富余；1GiB 可用但最紧（native ffmpeg 142MB/路，建议 +2GB swap，Docker 在 1GiB 上偏紧，首选裸二进制 + systemd + apt ffmpeg）；40GB 宽裕；**流量是主约束**：30Mbps ≈ 5–6 路 1080p，1024GB/月 ≈ 670 观看小时（个人/家庭宽裕，多人分享需压画质/关预缓存/开 302 直连）。
- 部署资料：仓库自带 Dockerfile/compose（bookworm-slim + ffmpeg + tini，UID 1000）、README 有 VPS 调优章节（原始 MP4/HLS 播放省 CPU、直连省流量、播放资源限流）。
- 灌流复现方法（本次实践）：viewer GET 两次拿 id → POST playback/open {dramaId} → GET playback/stream?session&episode&start=0&quality=0&version=0&remux=0（服务端忽略 Range 上限直接给整集）；native：POST playback/hls/open 后取 index.m3u8 + segment.ts。

- admin 初始化：`timeout 40 ./bin/juku -listen 127.0.0.1:8998 -admin-password ...` 首启后杀掉，再交给 systemd。**不要把密码写进 unit**。

  - **必须排除**：accounts.json（旧 admin 哈希）、viewer-key、juku.json（含宿主路径/代理）、ui-state.json（任务历史）、huangguo-session.json。

## 线上改为「必须登录 + 关闭注册 + 登录页前置」（零代码改动）

- 结论：**不要改代码**，程序已内建该策略。管理员 POST `/api/ui/admin/settings` `{requireLogin:true, allowRegistration:false}` 即可，持久化在 `data/accounts.json`，重启保持。UI 里对应「用户/账号」面板的 `adminRequireLogin` / `adminAllowRegistration`（`users.js:95/113`）。
- 生效后实测（匿名全新 cookie jar）：
  - `GET /` → 302 `Location:/login`；`GET /login` → 200
  - 全部 `/api/ui/*` 数据接口 → 401 `login_required`
  - `POST /api/ui/account/register` → 403 `registration_disabled`
  - `GET /api/ui/viewer`（二次调用）→ `requireLogin:true, allowRegistration:false, account:null`
- 关键实现位置（后续排查用）：
  - `account_admin.go:120 withAccountAccess`：`/assets/**` 无条件放行；`/api/ui/viewer`、`account/login|register|logout|password` 放行；其余 `requireLogin && account.ID==""` → 401；`/` 匿名 → 302 `/login`，`/login` 已登录 → 302 `/`。
  - **`ui_server.go:715 handleIndex` 只服务 `/` 与 `/login`，都返回同一份 SPA `uiHTML`**。
  - `main.js`：`if (app.account.init()) return;` —— 登录页模式下**整个主应用初始化中止**（偏好/用户/Emby/shell.access/历史/排行榜/`[settings,library,downloads,following].init()` 全跳过），数据零加载。
  - `account.js:124`：`loginPage = pathname==='/login' || forcedPassword || viewer.requireLogin && !account`；加 `body.account-page` 类，隐藏关闭按钮与「匿名使用」链接；CSS `.account-page` 隐藏 `.workspace/.desktop-nav/.header-actions/.mobile-nav`。
  - `account.js:133/134`：`allowRegistration===false` 时隐藏注册入口与提示。
- 已知遗留放行面（本实例无影响）：`withAccountAccess` 对 `/api/emby/media/`、`/api/emby/stream.m3u8`、`/api/emby/segment.ts`、`/api/emby/cover` **无条件放行**；若将来启用 Emby 集成，这会成为免登录入口，需另行加签或鉴权。本实例 `juku.json` 无 emby 字段、无 emby 数据文件，故不可达。

## 省内存版：剧库改磁盘分片缓存（分支 perf/library-disk-cache）

- 提交顺序：master 先提交 docs（51d161f，记忆整理 + 当日实测），再从它切 `perf/library-disk-cache` 提交剧库改造（f8cfe20，48 文件）。两分支都已推送（走 7897 代理）。
- 设计：内存只留精简索引 `dramaEntry`（静态 376B vs Drama 720B）；完整记录按 ID 的 FNV-1a 哈希分 256 片存 `data/library/records/NNN.json`，索引单独 `data/library/index.json`；LRU 缓存 16 片，**脏分片在淘汰时就地落盘**（否则会无限增长）。
- 落地文件：新增 `library_entry.go`（索引条目 + `drama()`/`applyEntry` 互转）、`library_store.go`（分片存储 + UIApp 访问器）、`library_store_test.go`（7 个用例）；`ui_server.go` 的 `dramas []Drama` 换成 `library *libraryStore`。
- 踩坑（重要）：
  1. `evictShardsLocked` 初版对脏分片「放回队尾重试」→ 全脏时**死循环**，测试挂 9 分钟。改为脏分片就地 flush 后再淘汰 + attempts 上限。
  2. `loadShardLocked` 命中缓存时没调 evict → 分片永不淘汰（实测常驻 132 片）。命中路径也要 evict。
  3. `upsert` 先用 incoming 建索引再合并磁盘记录 → 索引与记录不一致。改为先算合并结果再重建索引。
  4. `readLibraryCache` 原本只读旧 `library.json` → 一批测试读不到新落盘数据。改为优先读分片剧库、回落到旧文件；CLI 刷新额外同步写回分片。
  5. 保真（`reflect.DeepEqual` 测试）：`drama()` 有完整记录时必须以记录为准回填 Cover/EpisodeCount；`applyEntry` 不写这两个字段；封面为空时保持 nil 不能变成 ""；不要在 `drama()` 里给 Name 补 Title（会让 mergeRefreshedDrama 误判「标题被改」而回滚）。
- 实测（真实 27,722 部库，同机对比 base vs disk）：
  - 索引常驻 51.5 MiB vs 全量 74.2 MiB（索引字段：Desc 7.5 + Intro 7.5 + Cover 4.3 + Title/Name 各 1.8 + 其他 2.4 MiB）
  - 进程**空闲 RSS 177.8 → 136.4 MB**（-41MB）
  - `/api/ui/dramas` 5 次均值 0.242s → 0.204s（载荷 50.7 → 48.1MB，反而更快）；search/suggest 无退化
  - 磁盘：index.json 37MB + records 49MB（原 library.json 50.6MB，未删留作回滚）
- 遗留：整库一次性 JSON 编码仍会造成 ~400MB 瞬时峰值（Go 不立即还内存），两版都有；如需进一步压内存可考虑列表分页/响应后 FreeOSMemory。

### 第二轮：流式编码 + 简介去重（5ec6d3d）

- 发现真正的内存大头不是常驻，而是**瞬时峰值**：原版 6 次整库请求后 RSS 冲到 423MB 且 3 分钟不回落（Go 不把内存还给 OS）。
- 根因：`json.Encoder.Encode` 会先把整个值编进一个缓冲区再写 → 每次列表请求多出 48MB 缓冲 + 20MB `[]Drama`。
- 修法：新增 `writeLibrarySnapshot`（头字段正常编码，剧集逐条 `json.Marshal` 后按 8KB 分块写出）；
  `librarySnapshotLocked`/`librarySnapshotForSourceLocked` 改返回 `(map[string]any, []dramaEntry)`，
  排序统计新增 `needsSortMetadataEntry`/`sortMetadataRemainingEntries` 直接在条目上算。
  **注意**：返回的条目必须是副本（`append([]dramaEntry(nil), ...)`），因为编码发生在释放 `a.mu` 之后，持有活切片会数据竞争。
- 简介去重：23,578/27,722 部剧 intro==desc，索引只在两者不同时存 intro，`entryIntro` 读回时补。
- 踩坑：`dramaEntry` 加 `MarshalJSON` 补 intro 会让每条多一次 compact 扫描，响应从 28.7MB/0.186s 变成 36.9MB/0.365s → 改为
  intro 用 `omitempty`（与 desc 相同时直接不输出），前端 `dramaSearchText` 用 desc 就够。
- 最终实测（27,722 部）：常驻堆 74.2 → **19.7 MiB**；空闲 RSS 177.8 → **109.4 MB**；
  6 次整库请求后峰值 423.6 → **256.6 MB**；`/api/ui/dramas` 50.7MB/0.242s → **28.7MB/0.186s**。
- 剩余大头：每次列表请求仍要复制 10.4MB 条目切片（必须在解锁后使用副本）。若要再降需把 entries 改成写时复制（不可变快照）。
