## 8998 完全版资源实测 + VPS 适配评估（用户拟迁至 2C1G / 30Mbps / 40GB / 月1024GB 流量）

- 后台启动 `dist/juku.exe -open=false`（PID 19728），实测完整播放链路（viewer → playback/open → playback/stream 与 hls native）。
- 关键数据：
  - 空闲 RSS 106–186MB（library.json 50MB / 27,722 部全量在内存）；15 线程。
  - MSE 单流 78.5MB/34.7s（≈18Mbit/s）CPU 仅 +0.23s；2 路并发 129.7MB、CPU +0.44s、RSS +2.7MB。每 10Mbit/s 代理吞吐 ≈0.4% 单核、+1–3MB。
  - Native HLS（手机路径）：整集一个 ffmpeg 进程连续封装（RSS ~142MB），135s 1080p 全程 ~11s CPU（`-c copy` 封装非真转码）；占 "video" 额度（默认 1，故同时仅 1 路）。分片命中缓存后 1ms 级响应。
  - 并发上限来自 `data/playback-settings.json`（默认 会话4/媒体8/remux2/音视频转码各1/预备1/封装缓存512MB）；超限返回 429「同时播放数量已达上限」；会话空闲 10 分钟（playbackIdleTimeout）回收。
  - 1080p 竖屏（1080×1920）单片 147.6s / 78.5MB / 4.25Mbit/s → 1.53GB/观看小时。
- 结论：2 核富余；1GiB 可用但最紧（native ffmpeg 142MB/路，建议 +2GB swap，Docker 在 1GiB 上偏紧，首选裸二进制 + systemd + apt ffmpeg）；40GB 宽裕；**流量是主约束**：30Mbps ≈ 5–6 路 1080p，1024GB/月 ≈ 670 观看小时（个人/家庭宽裕，多人分享需压画质/关预缓存/开 302 直连）。
- 部署资料：仓库自带 Dockerfile/compose（bookworm-slim + ffmpeg + tini，UID 1000）、README 有 VPS 调优章节（原始 MP4/HLS 播放省 CPU、直连省流量、播放资源限流）。
- 灌流复现方法（本次实践）：viewer GET 两次拿 id → POST playback/open {dramaId} → GET playback/stream?session&episode&start=0&quality=0&version=0&remux=0（服务端忽略 Range 上限直接给整集）；native：POST playback/hls/open 后取 index.m3u8 + segment.ts。

## 正式部署到 VPS（111.91.25.138，Debian 12 x86_64，2C / 800MB / 40GB）

- 源码：避免污染 `perf/library-disk-cache` 的 WIP，**用 `git worktree` 检出 master（dbff3c3）**到临时目录后交叉编译。本地 master 仅比 origin/master 多一个 docs 提交，功能等价。
- 编译：`CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags="-s -w"` → 17.0MB 静态二进制（无 cgo 依赖，可 `-trimpath`）。17s 完成。
- 部署路径：二进制 `/opt/juku/bin/juku`，数据 `-data-dir /opt/juku/data`，systemd 单元 `/etc/systemd/system/juku.service`（WorkingDirectory=/opt/juku，TZ=Asia/Shanghai，Restart=always，LimitNOFILE=65535）。
- ExecStart：`-ui -listen 0.0.0.0:8998 -open=false -data-dir /opt/juku/data -ffmpeg /usr/bin/ffmpeg`。
- admin 初始化：`timeout 40 ./bin/juku -listen 127.0.0.1:8998 -admin-password ...` 首启后杀掉，再交给 systemd。**不要把密码写进 unit**。
- 依赖：`apt-get install -y ffmpeg ca-certificates tzdata` → ffmpeg 5.1.9；`ssh tool` 无 sshpass/rsync，用 Python paramiko 脚本做 SSH/SFTP 自动化（脚本在 `%TEMP%\juku-deploy\`）。
- 库迁移：本地 master 的 `libraryCache` 结构与现有 library.json **完全对齐** → 直接 gzip（50.6MB→8.3MB）上传后 gunzip 即可，服务端确认「已恢复本地剧库：27722 部」。
  - **必须排除**：accounts.json（旧 admin 哈希）、viewer-key、juku.json（含宿主路径/代理）、ui-state.json（任务历史）、huangguo-session.json。
- 端到端验证：首页 200/46KB；viewer 握手（首次无 id，带 guest cookie 二次取到 id）；admin 登录 200 且 `admin:true` 六源齐全；`/api/ui/search?q=总裁` → total 104 / 返回 19 条（`limited: true` 分页截断，注意参数名是 **q 不是 keyword**）；app.log 出现真实 `playback.started` / `playback.mode=MSE transcode`。
- **重要修正（与本机实测差异）**：VPS 上播放期 juku RSS 冲到 **477MB**（本机空闲仅 106–186MB），主因是 `cacheMB` 默认 512 的封装缓存 + 50MB 库常驻。800MB 机器单路播放后 available 只剩 53MB，**并发第二路极可能 OOM**。建议在管理后台调低：cacheMB 128–192 / maxSessions 2 / maxRemuxJobs 1（管理员界面可改，无需重启）。
- swap 陷阱：用户事前已建 2GB `/swapfile` 且已在 fstab，但 **`vm.swappiness=0` 导致 swap 完全不作为**；已写 `/etc/sysctl.d/99-juku.conf` 设为 10 并 `sysctl -w` 生效，swap 随即开始使用。
