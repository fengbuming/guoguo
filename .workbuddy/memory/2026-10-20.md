- 实测（本机 27,762 部，Windows WS）：
  | 场景 | juku | ffmpeg 合计 |
  |---|---|---|
  | 冷启动空闲 | 118.4 MB | 0 |
  | 热空闲（翻过列表） | 159.6–165.4 MB | 0 |

- 易错点纠正：`CacheMB=512`（`playback_generated.go` 的 `accountCache`）是**磁盘**配额，`os.MkdirTemp` 落 `/tmp`，不占 juku RSS；只有 `/tmp` 是 tmpfs 时才变内存。真转码大头是 ffmpeg 自身。
- 已存在但未启用的「转嫁」机制：`playbackSettings.DirectSources` + `allowPlaybackDirect`（`playback_direct.go`）→ plan 阶段给 `Delivery="redirect"`，客户端直连源站。本机无 `data/playback-settings.json` 即全默认（DirectSources 空）。红果因 CENCKey/凭据无法直连；无凭据源（cloudfront/dsd/黄果系）可通过 CORS + 206 探测后直连，可完全省掉 ffmpeg 与该路流量。
- 封面：`ui_image_cache.go` 内存 LRU 上限 32MB / 512 条 / 24h TTL，响应已带 `private,max-age=86400`（浏览器侧已缓存）。这是可磁盘化或转嫁客户端的纯服务端开销。
- 列表端点无 gzip：27.4MB 实测 gzip-6 → 6.94MB（3.95x，CPU 0.574s）/ gzip-1 → 7.86MB（0.283s）。实时压缩在 2 核 VPS 上代价明显，更优解是**语料变更时预渲染 `snapshot.json.gz` 落盘 + ETag + ServeContent**，请求期零 CPU 零内存。

## 三项优化落地（commit 5d2d0b2）

### 1. 列表响应预渲染为磁盘 gzip 快照（新文件 `library_snapshot.go`）

- 键 = sha256(排好序的头字段 + 条目数 + 站源作用域签名)；文件 `data/library/snapshot/<key>.json.gz`，LRU 保留 6 份。
- 请求期 `http.ServeContent`（sendfile），带 `ETag` + `Cache-Control: private, no-cache`；`If-None-Match` 直接 304。
- 头字段必须**按键排序**输出，否则同一状态渲染出的字节不一致（`writeLibraryObjectJSON` 里已排序）。
- 客户端不支持 gzip / 非 GET/HEAD / `entries==nil` 时全部回落原流式编码，任何写盘或读盘异常也回落。
- 作用域签名见 `librarySnapshotScopeKey`：不同账号可见源不同，不能共用快照（否则越权暴露条目）。
- 实测（27,762 部）：27.4MB → **7.09MB**（3.87x）；首次渲染 0.539s，命中 **0.024s**，304 零字节；不支持 gzip 仍是 27.43MB 且内容逐字段一致。
- 4 个测试：`TestLibrarySnapshotMatchesStreamedEncoding` / `RevalidatesAndRendersOnChange` / `KeySeparatesSourceScopes` / `PrunesOldFiles`。

### 2. 封面内存缓存 32MiB → 8MiB（`ui_image_cache.go`，条目 512 → 256）

响应已带 `private, max-age=86400`，重复访问本由浏览器消化，服务端只保留合并并发回源的余量。

### 3. 播放直连：实测结论与预期不同

- **开关 `data/playback-settings.json` 的 `enabled` 才是关键**：默认 false 时 `/api/ui/playback/plan` 一律返回 `player=legacy, reason=optimization_disabled`，前端回落到 `/stream` 的 **libx264 全量转码**。
- 逐源实测 `allowPlaybackDirect`（6 个源全加进 directSources）：**0 个通过**，全是 `delivery=proxy`。原因是源站不给 CORS / 需要凭据，`redirect` 实际不可得。
- 因此最终配置：`enabled=true, directSources=[]`（置空还能省掉每次 0.2–3.0s 的直连探测）。
- 效果：huangdou / cloudfront / huangguoai / huangju **改走纯 Go 代理，零 ffmpeg**（m3u8 0.01–0.02s，首片 26–91ms，实测真实出流）。
- 红果仍 `video_codec_unsupported → legacy`：加密流探测不出编码，回落到 `/stream` 转码。

### 4. 红果转码的真实代价（本次最关键数据）

- 采样 `Get-Process *ffmpeg*`：CPU 增量 34.37s / 墙钟 14.4s = **238.7% 单核**，RSS **139.2MB**。
- 即 2 核 VPS 上**一路红果就吃满两个核**；而代理路径（黄豆/帝果/黄果/剧果）ffmpeg 为 0。
- 根因：`playbackNativeArgs`/`playbackFFmpegArgs` 走 `playbackEncodingArgs` = libx264 veryfast + `-threads 2` 实时重编码。红果源本身是 H.264/AAC，只需解密+封装即可（`-c copy`），预估可降到 ~0.1 核。
