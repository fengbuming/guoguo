## 三项优化落地（commit 5d2d0b2）

### 1. 列表响应预渲染为磁盘 gzip 快照（新文件 `library_snapshot.go`）

- 键 = sha256(排好序的头字段 + 条目数 + 站源作用域签名)；文件 `data/library/snapshot/<key>.json.gz`，LRU 保留 6 份。
- 请求期 `http.ServeContent`（sendfile），带 `ETag` + `Cache-Control: private, no-cache`；`If-None-Match` 直接 304。
- 头字段必须**按键排序**输出，否则同一状态渲染出的字节不一致（`writeLibraryObjectJSON` 里已排序）。
- 客户端不支持 gzip / 非 GET/HEAD / `entries==nil` 时全部回落原流式编码，任何写盘或读盘异常也回落。
- 作用域签名见 `librarySnapshotScopeKey`：不同账号可见源不同，不能共用快照（否则越权暴露条目）。
- 实测（27,762 部）：27.4MB → **7.09MB**（3.87x）；首次渲染 0.539s，命中 **0.024s**，304 零字节；不支持 gzip 仍是 27.43MB 且内容逐字段一致。
- 4 个测试：`TestLibrarySnapshotMatchesStreamedEncoding` / `RevalidatesAndRendersOnChange` / `KeySeparatesSourceScopes` / `PrunesOldFiles`。

### 2. 封面内存缓存 32MiB → 8MiB（`ui_image_cache.go`，条目 512 → 256）

响应已带 `private, max-age=86400`，重复访问本由浏览器消化，服务端只保留合并并发回源的余量。

### 3. 播放直连：实测结论与预期不同

- **开关 `data/playback-settings.json` 的 `enabled` 才是关键**：默认 false 时 `/api/ui/playback/plan` 一律返回 `player=legacy, reason=optimization_disabled`，前端回落到 `/stream` 的 **libx264 全量转码**。
- 逐源实测 `allowPlaybackDirect`（6 个源全加进 directSources）：**0 个通过**，全是 `delivery=proxy`。原因是源站不给 CORS / 需要凭据，`redirect` 实际不可得。
- 因此最终配置：`enabled=true, directSources=[]`（置空还能省掉每次 0.2–3.0s 的直连探测）。
- 效果：huangdou / cloudfront / huangguoai / huangju **改走纯 Go 代理，零 ffmpeg**（m3u8 0.01–0.02s，首片 26–91ms，实测真实出流）。
- 红果仍 `video_codec_unsupported → legacy`：加密流探测不出编码，回落到 `/stream` 转码。

### 4. 红果转码的真实代价（本次最关键数据）

- 采样 `Get-Process *ffmpeg*`：CPU 增量 34.37s / 墙钟 14.4s = **238.7% 单核**，RSS **139.2MB**。
- 即 2 核 VPS 上**一路红果就吃满两个核**；而代理路径（黄豆/帝果/黄果/剧果）ffmpeg 为 0。
- 根因：`playbackNativeArgs`/`playbackFFmpegArgs` 走 `playbackEncodingArgs` = libx264 veryfast + `-threads 2` 实时重编码。红果源本身是 H.264/AAC，只需解密+封装即可（`-c copy`），预估可降到 ~0.1 核。

### 5. 加密源改走 remux（commit 4a57978，`ui_playback_plan.go`）

- 改动：`convert` 分支里判断 `len(media.media.CENCKey) > 0` → **跳过 `probePlaybackCodecs`**，直接 `generatePlayback(processing="remux")`。原因：CENC 流解密前探测不出 codec，`info.Video==""` 会被误判为 `video_codec_unsupported` 而落到 legacy 全量重编码。
- 同时：加密流无法判断音频编码，`processing` 强制保持 `remux`（不再切 `audio`）。
- 失败仍可回落：`generatePlayback` 返回 `playbackOutputError` → `legacy/generated_output_incomplete` → 前端 `fallbackPlanned` 把 `planMode` 置 `legacy`（`processing!='original'` 时），链路完整、有 2 次上限。
- 实测同一集（147.6s 1080p）：plan **0.67s** 产出 40 片 fMP4（EXTINF 4.27s、含 init.mp4，首片 `styp/msdh` 合法），首片即点即得；三集连续 remux 累计 ffmpeg CPU **0.23s**（≈0.08 核秒/集），此前单集约 350 核秒、实时占用 2.4 核。
- 并发额度从 `video`（MaxVideoTranscodes=1）变成 `remux`（MaxRemuxJobs=2）→ 同时可跑两路，原来只能一路。
- **代价**：plan 现在要等整集封装完才返回（首帧等待 0.67–9.11s，取决于红果 CDN），此前是边转边播首帧 ~1.1s。若嫌慢，可让 CENC 源改走 `/stream?remux=1` 渐进式 `-c copy`（首帧快，但 `-ss` 跳转只认 offset==0，跳转要重新转码）。
- 既有易波动测试：`TestPlaybackNativeHLSSeeksRangesPrefetchAndCleanup`（真实 ffmpeg + 30s 批次）在全量跑中偶发 `prefetch must describe partial caching`（单跑必然通过），机器抢 CPU 时更容易复现。

## 播放：首帧不等整集封装（commit 93e702e）

- `generatePlayback` 改为**首分片落盘即返回**（上限 2.5s），生命周期（结算磁盘缓存、落定清单、释放额度、关输入代理）移到独立收尾协程；`jobCtx` **不再挂 plan 请求的 ctx**（否则 plan 一返回 ffmpeg 就被 cancel，边生成边播当场断流）。
- `progressivePlaylist()` 改写正在增长的 index.m3u8：URI 换本地地址、`PLAYLIST-TYPE` VOD→**EVENT**（未写完就声明 VOD 会让播放器停止轮询）、注入 `EXT-X-START:TIME-OFFSET=0` 从 0 起播、裁掉末尾悬空标签（ffmpeg 原地重写清单，可能读到写了一半）。跑完切到校验过的完整 VOD 清单，播放器见 ENDLIST 转点播，拖动区间随之完整。
- 一个分片都没产出 ⇒ `failed=true`，ServeHTTP 回 410 让播放器立刻重试；空清单兜底用 `playbackGeneratedEmptyPlaylist`（EVENT + TARGETDURATION，播放器按 live 重试而不是判坏流）。
- 测试需 `waitPlaybackGenerated(t, generated)` 等收尾再断言完整索引（`playback_plan_test.go` / `emby_playback_test.go` 已改）。

## 服务端内存（commit 7efa6a5）

用户明确：**VPS 内存吃紧，优先压服务端内存**。

实测（27,762 部，Windows，4 并发整库 `/api/ui/dramas` 27.4MB 未压缩）：
- 基线：空闲 38MB → 峰值 **256MB** → 20 秒后仍 **240MB**（Go scavenger 渐进，RSS 不落）
- 现在：峰值 **111MB**，5 秒 79MB，20 秒 **69MB**；整库响应 0.40s → 0.21s
- 单独 GOGC=50 只把峰值 111→102（收益有限，主要收益来自不按条分配）

改动要点：
1. `writeLibraryObjectJSON` 复用 `json.Encoder` + 一个 `bytes.Buffer`，替代逐条 `json.Marshal`（整库一次请求约 28MB 垃圾）。Encode 输出 = Marshal + 一个换行（已 `TrimSuffix`），**字节完全一致**（快照 key 依赖这点）；`SetEscapeHTML` 必须保持默认，否则字节变。
2. `libraryStore.Entries()` 发布**共享只读快照**（`published`/`publishedDirty`/`publishedAt`），库变更后第一次读才复制一次；`librarySnapshotLocked` 不再每请求复制 10.4MB。所有就地修改 `s.entries` 的地方（importDramas/upsert/Update/SortByTitle/UpdateEntries/Remove）都要 `entriesChangedLocked()`。
3. 两级尾部回收 `UIApp.releaseRuntimeMemory()`：1s 后 FreeOSMemory；35s 后（无新请求）`dropIdlePublished(30s)` 丢掉空闲快照再回收。调用点：`handleDramas`（entries≥1000）、快照渲染完、`loadLibrary` 末尾。
4. `configureProcessMemory()`（`memory_limit.go`）：未设 `GOMEMLIMIT` 时取 cgroup/物理内存的 **45%**（下限 192MiB，上限 1.5GiB）；≤4GiB 且未设 GOGC 时 `SetGCPercent(50)`；Linux 设 `GODEBUG=madvdontneed=1`（默认 MADV_FREE 归还后 RSS 不降，监控像没降）。
- 验证手法：`.workbuddy/tmp/mem_probe.py <pid> <并发> <轮数>`（ctypes 读 psapi，Windows WS/private）；`single_probe.py` 看单请求后回落。FreeOSMemory 微基准在 `.workbuddy/tmp/gochk`：私有提交 174MB → 13.7MB，证明机制有效。
- 剩余：空闲 69MB 里约 30MB 是峰值后的堆碎片（FreeOSMemory 只还整块空闲 span）；Linux + GOGC=50 会更低。**磁盘/客户端可转移项**见回复。
- VPS 侧待做：换二进制 + `data/playback-settings.json` 的 `cacheMB` 512→192（page cache 压力）。
